## What the incremental download path would need to change (analysis only)

For `rs_v2_clean` to become the daily-pipeline dataset, at minimum:

1. **The 4-date gap must be formally resolved as a policy decision, not a data fix** — the data provably doesn't exist at IEX for those exact sessions. Options: (a) accept and formally register these as reviewed exceptions in `rs_v2_clean_coverage_exceptions.json` with an explicit, documented rationale (currently that file is empty — nothing has been through review), or (b) switch data feed from `iex` to `sip` (paid tier) or a different provider for just these sessions, or (c) accept the strategy operates with known local NaN/forward-fill handling for these 4 dates specifically and validate that doesn't leak into signal generation. None of these are implementation-free.
2. **The 2025-03-10 / 2024-12-23 full-universe intraday gaps need root-causing separately** — these are `PROVIDER_WIDE_PATTERN`, not the known legacy 4 dates, and affect QQQ/SPY benchmarks too, which the 4-date gaps do not.
3. **`--refresh-latest` incremental logic (used by `scripts/run_daily_paper_pipeline.bat` against `hisseler/`) has no equivalent proven yet against `rs_v2_clean`'s stricter schema.** The `rs_v2_clean` acquisition path is a full, exact-contract, all-360-item batch acquisition with per-file SHA256 and frozen-baseline hash checks — none of that machinery has been exercised in an incremental "just fetch today's bar" mode. Building and testing that incremental path is separate work, currently not started (`Full recovery, new acquisition, strict validation, canonical backtest, research package, and shadow pipeline: NOT_STARTED / NOT_RUN` per the milestone report).
4. **`data_engine.py` / `universe_scanner.py` / the strategy/portfolio layers currently point at `testdata/hisseler/`** (confirmed in the prior repo audit); repointing them at `rs_v2_clean_market_data/` is itself an implementation task deferred until the above is resolved — explicitly out of scope for "analysis only" here.

## Final Recommendation

**NO-GO.**

Reasoning:
- The dataset's own strict validator already recorded `FAILED_VALIDATION` and that status is current (no mutation since).
- The failure is not marginal: 0% intraday coverage pass rate, ~31% daily coverage pass rate, zero approved exceptions.
- The specific 4-session gap this migration was meant to fix is **provably unresolvable at the current data provider/feed** (Alpaca IEX) — this is a hard external blocker, not a bug to patch.
- Existing repo evidence shows the gaps are large enough to visibly distort monthly portfolio composition (up to 108 rank positions on one date), so this isn't a cosmetic data-quality nit — it would change actual BUY/SELL decisions.
- No incremental daily-refresh path exists yet for `rs_v2_clean` even if the data problem were solved.

This does not mean the `rs_v2_clean` effort was wasted: the coverage-forensics and repairability tooling built for it is more rigorous than anything `hisseler/` currently has, and is worth keeping/reusing regardless of which dataset wins. But cutting the daily pipeline over today would mean shipping a dataset that fails its own designed-in safety gate — directly contrary to this project's own "fail-closed, never continue under uncertainty" principle (HANDOFF.md, ADR-002).
